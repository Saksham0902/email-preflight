Email Preflight — Setup

How to get the panel into your org and open it

Created by Saksham Mathur  |  Last updated: September 2026

This document has two parts, and most people only need the second one.

Part Who does it How often
Part 1 — Deploy it to the org Someone who can deploy metadata Once per org
Part 2 — Open it in the builder Anyone building or reviewing emails Every time you use it

If somebody has already deployed it to your org, skip to Part 2 — it is three clicks and no setup.

There is nothing to configure. Email Preflight is three Lightning Web Components and nothing else — no Apex, no Named Credential, no permission set, no connected app, no custom object. Deploy it and it works.
About the commands in this guide. Anything highlighted like this is a placeholder — replace it with your own value, including the highlighting itself. Everything else is typed exactly as written. There are only three placeholders in the whole document:

MyOrg Any short nickname you choose for the org. You are inventing this, not looking it up mcn-uat

Part 1 — Deploy it to the org

What you need first

Requirement Notes
Marketing Cloud Next With the extension panel available in the email builder
Permission to deploy metadata Usually a System Administrator, or a developer with Modify Metadata
Salesforce CLI Check with sf --version. If it is missing, install it from developer.salesforce.com/tools/salesforcecli
Visual Studio Code (optional) Only for the point-and-click alternative in Step 4. The commands work in any terminal
Node.js (optional) Only needed if you want to run the test suite in Step 3

Step 1 — Unzip it and open a terminal there

Unzip Email-Preflight.zip somewhere you can find again — your Desktop or Documents is fine. Do not work inside the zip preview window that Windows shows when you double-click the file; nothing you run will see those contents.

The unzipped folder should contain these, all at the same level:

Email-Preflight/
  README.md
  Email-Preflight-Overview.html
  Email-Preflight-Setup.html
  sfdx-project.json          <-- this file is how you know you are in the right place
  force-app/

Now open a terminal in that folder. Everything from here on assumes you are inside it.

The reliable way, on either platform: open the folder in File Explorer or Finder first, then open a terminal from it — on Windows, type cmd into the address bar and press Enter; on a Mac, right-click the folder and choose New Terminal at Folder. Doing it this way means you never type a path at all, which removes the most common way this step goes wrong.

If you would rather type it:

cd "path/to/Email-Preflight"

Then confirm you are in the right place. This should list sfdx-project.json:

dir        (Windows)
ls         (Mac or Linux)

"The system cannot find the path specified" / "no such file or directory"
The path is wrong, or it has a space in it and you left the quotes off. Keep the quotation marks exactly as shown above — cd "C:\Users\jane\My Files\Email-Preflight" works, cd C:\Users\jane\My Files\Email-Preflight does not.

You are in a folder that contains only another folder of the same name
Some unzip tools nest the folder inside itself, so you end up with Email-Preflight/Email-Preflight/. Go one level deeper. The correct folder is whichever one directly contains sfdx-project.json.

You cannot see sfdx-project.json in the listing
You are in the wrong folder — most often one level too high, or still in Downloads. Being in the wrong folder here is what makes Step 4 fail later with a confusing message about missing source, so it is worth getting right before moving on.

You were sent the full project rather than the zip
Then the folder is called emailPreflight and contains extra developer files. Same rule applies: the right folder is the one holding sfdx-project.json.

Step 2 — Connect to your org

The login URL is the only thing that differs between a sandbox and a production org, so pick the matching line:

# Sandbox
sf org login web --alias MyOrg --instance-url https://test.salesforce.com

# Production or a developer org
sf org login web --alias MyOrg --instance-url https://login.salesforce.com

MyOrg is a nickname you are making up, not something to look up. Pick something you will recognise in a month. Filled in, the sandbox line looks like this:

sf org login web --alias mcn-uat --instance-url https://test.salesforce.com

A browser window opens. Log in with that org's credentials and it closes by itself.

If your org uses a custom My Domain and neither URL above works, pass the domain straight in:

sf org login web --alias MyOrg --instance-url https://your-domain.my.salesforce.com

Then confirm it worked:

sf org list

Your alias should be listed with the right username. Read the username rather than glancing at it — if you have several orgs connected, deploying to the wrong one is the easy mistake to make.

"sf is not recognised" / "command not found"
The Salesforce CLI is not installed, or the terminal was already open when it was installed. Close the terminal, open a new one, and run sf --version. If that still fails, install the CLI from developer.salesforce.com/tools/salesforcecli and open a fresh terminal afterwards.

The browser opens but login fails, or it says you are not authorised
Check you used the right URL for the kind of org — a sandbox will not accept login.salesforce.com, and production will not accept test.salesforce.com. This is the single most common cause and the error message does not say so.

It logged you into the wrong org
Your browser was already signed in to another org and reused that session. Run the command again in a private or incognito window, or sign out of Salesforce in your browser first.

You already had this org connected under a different alias
Harmless — an org can have several aliases. Use whichever one sf org list shows against the username you want.

Step 3 — Run the tests (optional)

Skip this unless you were given the full project. The packaged copy deliberately leaves the test suite out — it is not needed to run the tool, and it triples the download. If your folder has no package.json in it, there is nothing to run here; go to Step 4.

With the full project, it is worth doing once if you have changed a rule, or to confirm the copy you were given is intact before it goes near an org.

npm install
npm run test:unit

You should see 557 passing tests across 3 suites, in about fifteen seconds. A failure here is a real bug in the rules, not a setup problem — nothing in the suite touches an org, so it cannot be caused by anything about your environment or your login.

Step 4 — Deploy

sf project deploy start --source-dir force-app --target-org MyOrg

Use the same alias you chose in Step 2 — so with the example from earlier:

sf project deploy start --source-dir force-app --target-org mcn-uat

It takes under a minute and reports three components:

Component What it is
emailPreflight The panel you see in the builder
preflightEngine The rules. Internal — it never appears in the builder menu
qaCompare The comparison logic behind the QA tab. Also internal

Deploy the whole force-app folder, not one component. The three are versioned together, and deploying the panel on top of an older engine produces findings that do not match what the panel says about them.

If you prefer not to use the terminal: open the emailPreflight folder in VS Code with the Salesforce Extension Pack installed, right-click the force-app folder in the explorer, and choose SFDX: Deploy Source to Org. That is a safe shortcut here precisely because there is no Apex in this project — for a deployment containing Apex it would be the wrong tool, since it gives you no way to set a test level.

"No source found" or "nothing to deploy"
You are not in the folder that holds sfdx-project.json. Go back to Step 1 — this is what that check was for.

It deployed, but to the wrong org
The alias after --target-org did not match the one you meant. Run sf org list, check the username, and deploy again with the right alias. No harm done: deploying these three components changes nothing else in an org, and re-deploying simply overwrites.

"Value too long for field: Description"
You are deploying a modified copy. Shorten the <description> in emailPreflight.js-meta.xml to under 255 characters.

It fails on Apex test failures
You are deploying to production. See the next section — this is expected and there is a way round it.

Step 5 — Confirm it landed

sf org open --target-org MyOrg --path lightning/setup/LightningComponentBundles/home

You should see Email Preflight listed, along with preflightEngine and qaCompare. Those two being present but never showing up in the builder is correct — they are marked as internal on purpose.

Deploying to production

Production deployments run Apex tests, and by default the CLI runs every test in the org. This project contains no Apex of its own, so if any unrelated test in your org happens to be failing, your deploy fails along with it — through no fault of the thing you are deploying.

To avoid that, validate first and name a test class that already passes in that org, then release the validated deployment:

sf project deploy validate --source-dir force-app --target-org MyOrg --test-level RunSpecifiedTests --tests SomePassingTestClass --wait 60

sf project deploy quick --use-most-recent --target-org MyOrg

Filled in, that first line looks like this:

sf project deploy validate --source-dir force-app --target-org acme-prod --test-level RunSpecifiedTests --tests AccountTriggerTest --wait 60

SomePassingTestClass is the one value here you cannot invent — it has to be a real Apex test class that currently passes in that org. If you do not know one, ask whoever maintains the org; "name me a test class that passes" is a quick question for them to answer.

The first command is long, but keep it on one line — the character that splits a command across lines differs between PowerShell, Command Prompt and a Mac terminal, and getting it wrong is a more confusing failure than a line that wraps on screen.

Validating first costs you nothing when it fails, which is the whole reason to do it in this order.

Part 2 — Open it in the builder

  1. Open an email in the Marketing Cloud Next builder. An email template or a reusable content block works too — the panel notices which it is and applies the checks that belong to it. Templates are worth running it on in their own right, since anything wrong in one is wrong in every email built from it.
  2. Click the extension panel icon in the toolbox.
  3. Choose Email Preflight.

It scans straight away. There is no button to press and nothing to set up the first time.

Click Re-check after you change something. The panel has two tabs — Email Issues for the automatic scan, and Email QA for checking the email against a copy deck. Both are covered in the overview document. The tab names follow whatever you have open, so on a template they read Template Issues and Template QA.

Give the first result a sceptical read. Do the link and image counts match what is actually in the email? The rules read Marketing Cloud Next's internal content structure, and unusual content can be shaped in ways they do not expect. If a finding looks wrong, see the last section.

Updating to a newer version

Replace the folder contents with the newer copy and run the same deploy command again:

sf project deploy start --source-dir force-app --target-org MyOrg

Nothing needs uninstalling first, and there is no stored state to migrate — the panel keeps nothing between sessions. Anyone with the builder open should refresh the page afterwards, otherwise they will keep running the version their browser already loaded.

Troubleshooting

Problems that belong to one particular step are answered next to that step, since that is where you will be when you hit them — see the grey boxes under Steps 1, 2 and 4. What follows covers everything after the deploy.

Symptom What to do
The deploy command is not recognised The Salesforce CLI is not installed or not on your PATH. Check with sf --version, and see the box under Step 2
Deploy fails saying it cannot find the source You are in the wrong folder. See the box under Step 1 — this is the most common early problem, and the fix is to cd into the folder containing sfdx-project.json
Deploy fails on test failures in production Unrelated Apex tests in that org are failing. Use the validate-then-quick approach above
Email Preflight is not in the toolbox menu Confirm the deploy succeeded (Step 5), then refresh the builder page. A browser that loaded the builder before the deploy will not see it
"Could not read the editor content" The editor returned nothing. Close the content item and reopen it
The panel says the content type is unsupported Expected. It works on emails, email templates and reusable content blocks — not SMS, push or landing pages
A shared footer block still shows as missing its unsubscribe link Expected. An email stores only a pointer to a content block, so the panel cannot read inside one. It names the block and tells you to open and check it separately
"This editor won't let the panel use the clipboard" The builder's frame is blocking clipboard access. The report text appears below the message — select and copy it by hand. The scan itself is fine

If a finding looks wrong

At the bottom of the Issues tab there is a Content structure section with a Copy structure button. Send that along with the rule ID and what you think it got wrong. That outline is what allows the rule to be corrected against the real content rather than a guess, and it is far more useful than a description of the problem.
